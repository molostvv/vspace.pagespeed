# vspace.pagespeed — скорость загрузки страниц

Модуль Битрикса, который заменяет ammina.optimizer:

1. **Critical CSS** — стили первого экрана встраиваются в `<head>`, полные CSS на телефонах и планшетах
   загружаются асинхронно, в head не остаётся блокирующих стилей. На компьютере (от 1024 px) полный CSS
   подключается как без модуля.
2. **Картинки** — первый экран грузится сразу (фон hero — с высоким приоритетом), всё ниже — по мере
   прокрутки.
3. **WebP** — браузерам с WebP вместо JPEG/PNG отдаются WebP-копии (в 5–15 раз легче); копии делает агент
   модуля из cron через GD, без облачных сервисов.
4. **Отложенный JS** — скрипты выполняются после загрузки страницы, когда полный CSS уже применён, и не
   мешают первому экрану.

Ammina после этого ничего полезного не делает — следующий шаг удалить её (см. «План»).

Почему свой модуль и что не так с Ammina — [docs/ammina-analysis.md](docs/ammina-analysis.md).

## Как это работает

```
OnBeforeEndBufferContent ── AmminaBridge: выключить у Ammina CSS, lazyload, JS и (если агент WebP работает) картинки
OnEndBufferContent (1100, после Ammina)
  RequestGuard ── GET, HTML, не админка/AJAX/правка, не в исключениях (страницы, домены, шаблоны);
                  AJAX-ответ с HTML-фрагментом — только WebP
  Optimizer
    Document ── позиции head/body, теги вне script/style/комментариев (без DOM, разметка не пересобирается)
    CriticalCssProcessor
      1. подключения CSS: <link rel=stylesheet> на локальные .css + крупные <style> из head
      2. первый экран: FoldDetector (шапка + N блоков .panel/.section, маркер <!--vps-fold-->)
         → AtomCollector: классы/id/теги первого экрана (+ cookie-баннер и т. п. из ADD_CLASSES,
           без содержимого скрытых меню из FOLD_SKIP_CLASSES)
      3. CriticalCssBuilder: индекс каждого CSS (кеш по mtime) → critical по атомам (кеш по сигнатуре)
      4. правки: preload + <style data-vps-critical> в head, <link media="(min-width: 1024px)" onload> + <noscript>
    ImagesProcessor (та же граница первого экрана)
      WebpRewriter: адреса JPEG/PNG → готовые копии /upload/vspace.pagespeed/webp/…; нет копии — в очередь
      выше: <img> без loading=lazy, фон hero → <link rel=preload as=image fetchpriority=high>
      ниже и в скрытых меню: <img>/<iframe> loading=lazy, фоны из style → data-vps-bg + скрипт
    DeferJsProcessor
      <script> → type="text/vps-defer" + загрузчик перед </body>: после onload — по порядку, на прежних местах
    Edits ── все правки применяются одним проходом
Агент Agent::webp() (cron Битрикса или cron.php модуля, раз в минуту) ── очередь → WebpConverter (GD) → копии
```

Правило попадает в critical, если хотя бы один селектор из его списка выполним на первом экране
(классы, id и теги есть в разметке). Это надмножество: `:not()`, `:is()`, атрибуты, `:nth-child` не
сужают выбор — лишнее правило безопаснее пропущенного. `:hover`/`:focus` и `@media print` не берутся,
`@font-face` — только для используемых семейств (с `font-display: swap`), `@keyframes` — только нужные.
Одинаковые правила из разных файлов выводятся один раз — последняя копия, каскад от этого не меняется
(наборы стилей страниц вроде `page-articles.min.css` повторяют шапку из `main.min.css`).

На компьютере полный CSS блокирует отрисовку, как без модуля: у асинхронной ссылки вместо `media=print`
стоит `media="(min-width: 1024px)"` (настройка «Полный CSS блокирует отрисовку на экранах от»). На широком
экране условие выполняется, и браузер ждёт файл до первой отрисовки, на узком — грузит без блокировки и включает
загрузчиком. Причина — TBT: включение 1.3 МБ полного CSS после показа — пересчёт стилей и раскладки всей
страницы одной задачей (на компьютере она сразу после первой отрисовки и попадает в TBT, без модуля — до неё и
не считается). PSI desktop на scilib.ru, `/articles/`: с critical 72–75 (TBT 500–925 мс), без critical 96–99
(TBT 19–92 мс), без модуля 85–93; главная 92–99 → 98–100. На телефоне critical нужен: статья «link-seo» 95–99
против 73–74 без него, главная 92–98 против 83–94. Определение по ширине экрана, а не по User-Agent, не мешает
кешу страниц.

Critical рассчитан на первый экран. Если страница открывается не сверху — перезагрузка или «назад» с прокруткой
ниже первого экрана, адрес с `#якорем`, — браузер сразу показал бы середину страницы без стилей, и она прыгала
бы, пока приходит полный CSS (на услуге «медицина» CLS 1.2), а потом ещё раз — когда отложенный JS сворачивает
слайдеры (до запуска они стоят в ряд узкими слайдами и вдвое выше). В этих случаях страница скрыта до включения
полного CSS и конца отложенного JS, не дольше 3 с; при перезагрузке с середины CLS стал 0.03.

Прокрутку при показе модуль восстанавливает сам — по элементу, который был в центре экрана: при уходе со
страницы в `sessionStorage` запоминается путь к нему и его высота на экране, при показе он возвращается туда же
(браузер восстанавливал позицию по ещё не свёрстанной странице и промахивался на сотни пикселей, по пикселям —
тоже: картинки выше экрана после перезагрузки ещё не загружены). Ещё 4 с после показа, до первого действия
пользователя, элемент удерживается на месте, если страница меняет высоту (на главной скрипты дописывают блоки
выше экрана). На scilib.ru все проверенные страницы возвращаются точно на прежнее место. Обычные переходы
(и замеры PSI) это не затрагивает.

Кеш — `/bitrix/cache/vspace.pagespeed/` (очищается вместе с кешем сайта и пересобирается сам):
`index/` — разобранные CSS-файлы (PHP, читаются из OPcache), `critical/` — готовые critical.
Вынесенные `<style>` отдаются браузеру, поэтому лежат в `/bitrix/cache/css/vspace.pagespeed/`: nginx BitrixVM
закрывает `/bitrix/cache/` целиком, кроме `css/*.css` и `js/*.js` (объединённые CSS/JS ядра). Сигнатура critical строится только из тех атомов страницы, которые
упоминаются в CSS, поэтому страницы одной структуры делят один файл. Правка CSS-файла меняет его mtime —
critical пересобирается без очистки кеша. Агент раз в сутки удаляет неиспользуемое дольше `CACHE_TTL_DAYS`.

Обычный запрос (всё в кеше) — 8–15 мс. Первая сборка после изменения CSS — 0.4–2 с (main.min.css весит
1.3 МБ); пока она идёт, параллельные запросы получают страницу без изменений.

### Картинки

- **Первый экран.** `loading="lazy"` у `<img>` снимается: его ставит на все картинки сайтовый
  `COptimisationImage` (`local/php_interface/classes`), а видимые сразу картинки не должны ждать. Фон hero —
  первая фоновая картинка в `style` после начала контента (`.page__content`), на страницах `demis_edges` это
  LCP — получает `<link rel="preload" as="image" fetchpriority="high">`: иначе браузер узнаёт о нём только
  после разбора CSS.
- **Ниже первого экрана и в скрытых меню** (`FOLD_SKIP_CLASSES`): `<img>` и `<iframe>` без `loading`
  получают `loading="lazy"`; фон из `style` переносится в `data-vps-bg`, а скрипт перед `</body>`
  (IntersectionObserver, запас 300px, без ожидания `window.onload`) возвращает его, когда элемент подходит
  к экрану. Клоны слайдеров, которые появятся позже, подхватывает MutationObserver.
- Откладывается только простой фон — одна картинка без градиентов, `image-set`, `!important`; остальные
  остаются как есть.
- Не трогаются элементы с `data-lazy="N"` (соглашение сайта) и `data-vps-skip`, `<img fetchpriority="high">`.

### WebP {#webp}

- **Где подменяется.** В `<body>` страницы и в HTML-фрагментах из ответов AJAX (блоки, которые страница
  подгружает скриптом, — на главной это отзывы, награды): `src`, `srcset`, `poster`, фоны в `style` и
  data-атрибуты, из которых картинку подставляют скрипты (`data-src`, `data-srcset`, `data-bg`,
  `data-image` — random.js, `data-adapt` — article-list.js, `data-poster` — видео на главной). Только
  локальные JPEG/PNG; ссылки (`href`), `<head>` (`og:image`) и CSS-файлы не трогаются.
- **Кому.** Браузерам с WebP: по заголовку `Accept`, а Safari (он не пишет WebP в `Accept`) — по версии:
  iOS 14+, Safari 16+ на macOS. Остальные (и поисковые роботы, которые не просят WebP) получают исходники.
- **Как появляются копии.** Страница конвертации не ждёт: нет копии — отдаётся исходник, а картинка
  ставится в очередь (`/upload/vspace.pagespeed/queue/`). Агент `Agent::webp()` раз в минуту из cron
  конвертирует очередь (до 20 с за запуск) через GD с качеством из настройки «Качество WebP» (по умолчанию 80)
  и кладёт копию рядом с путём исходника:
  `/upload/iblock/a/b.jpg` → `/upload/vspace.pagespeed/webp/upload/iblock/a/b.jpg.webp`. Исходник заменили —
  копия делается заново (время копии = времени исходника). Если WebP не меньше исходника на 5% (мелкие
  иконки) или картинку нельзя конвертировать (CMYK, больше 40 Мп, битый файл), остаётся исходник — пустой
  файл копии запоминает это, чтобы не конвертировать снова. Копии удалённых картинок удаляет суточный агент.
- **Без GD с WebP** (PHP собран без `imagewebp`) копии не делаются: адреса не подменяются и в очередь ничего не
  ставится, посетители получают исходники, WebP Ammina (если стоит) не выключается. На вкладке «Картинки» —
  строка «Конвертация» (версия GD и есть ли WebP) и ошибка над вкладками. Другие библиотеки (Imagick, cwebp) не
  поддерживаются: на BitrixVM GD с WebP есть (scilib.ru: PHP 8.1, GD 2.3.3).
- **Цена.** Проверка копии — два `stat` на картинку: на сервере ~1–2 мс на сотню картинок; постановка в
  очередь — доли миллисекунды и один раз.
- **Ammina.** Пока агент работает по cron, у Ammina на тех же страницах выключаются картинки
  (`AMMINA_DISABLE`): её WebP шёл через облачный сервис, с качеством 90 (наши копии на 40% легче), а
  `og:image` она подменяла относительным адресом своей SVG-копии. Если cron не работает, её WebP остаётся.

**Нужен cron.** На хите посетителя агент не конвертирует (20 с работы не должны достаться посетителю), поэтому
если агенты выполняются на хитах, копии не появятся — настройки модуля показывают предупреждение. На BitrixVM:

1. В `/bitrix/php_interface/dbconn.php` есть `define('BX_CRONTAB_SUPPORT', true);` — тогда на хитах
   выполняются только периодические агенты, а агенты модуля (непериодические) — только из cron.
2. У пользователя bitrix в crontab есть `* * * * * php -f /home/bitrix/www/bitrix/modules/main/tools/cron_events.php`
   (обычно BitrixVM ставит его сам; на scilib.ru его нет — агенты там не выполнялись с августа 2026).

Если cron Битрикса не настроен или его нельзя включить (он выполнит все накопившиеся агенты сайта и разошлёт
почтовую очередь — на копии сайта это лишнее), есть `cron.php` модуля: он выполняет только агенты
vspace.pagespeed, которым подошло время (WebP — раз в минуту, очистка кеша — раз в сутки), и сдвигает их
расписание, как это делает Битрикс. В crontab пользователя bitrix (не root — иначе сайт не сможет писать в
очередь):

```
* * * * * /usr/bin/php -f /home/bitrix/www/local/modules/vspace.pagespeed/cron.php
```

`php cron.php -v` — что выполнено и сколько копий и картинок в очереди, `--force` — не ждать времени агентов.
Со скриптом можно оставить и cron Битрикса: агент не выполнится дважды за интервал.

Работает ли — видно на вкладке «Картинки»: «Агент конвертации из cron — запускался N с назад».

### Отложенный JS {#js}

Полный CSS подключается асинхронно, а скрипты, которые при запуске измеряют вёрстку (слайдеры, липкая шапка,
waypoints), должны видеть уже полный CSS. Поэтому скрипты выполняются после `window.onload` — так же
делала Ammina (`type="deferjs"`), и так работает прод. Заодно ~2 МБ JS не занимают сеть и процессор, пока
грузится первый экран. На redesign заодно уходил сдвиг первого экрана (CLS на телефоне 0.085 → 0.003), но
сейчас этот шаблон модуль не обрабатывает (см. «Настройки»).

- У скриптов тип меняется на `text/vps-defer` — браузер их не качает и не выполняет. Загрузчик перед `</body>`
  после onload и первой отрисовки — события first-contentful-paint (страница с critical CSS часто успевает
  загрузиться раньше, чем браузер её нарисует, и скрипты, начатые сразу, отодвигали FCP/LCP: в PSI LCP 5–7 с
  вместо 2 с в части прогонов) выполняет их по порядку на прежних местах (`document.currentScript` и соседи в DOM — те же).
  Подряд идущие внешние файлы вставляются разом (`async=false`): качаются параллельно, выполняются по
  порядку — у Ammina они качались по одному, поэтому скрипты теперь отрабатывают на 0.5–4 с раньше.
  Встроенный скрипт ждёт предыдущие внешние; внешние с `async` — в самом конце.
- Отложенные скрипты сами не получат `DOMContentLoaded` и `load` — события уже прошли, а на них построена
  инициализация шаблона redesign (шапка, слайдеры, модальные окна) и waypoints в `main.min.js`. Загрузчик
  на время запуска запоминает такие обработчики (и `window.onload`) и вызывает их после всех скриптов, в том
  же порядке, что браузер. Обработчики, повешенные раньше, второй раз не вызываются.
- `document.write` на это время вставляет разметку после своего скрипта, а не стирает страницу. Ошибка в
  одном скрипте не останавливает остальные. Когда всё выполнено — `window.vpsJsDone = 1`.
- Не трогаются: `data-skip-moving` (соглашение Битрикса «не переносить»: на сайте это объявления данных —
  они нужны раньше, а не позже), `data-vps-skip`, файлы из «Не откладывать скрипты» (по умолчанию HeaderJilin
  и `inp.min.js` — их исключала и Ammina), JSON-LD и шаблоны, `type="module"`, `nomodule`.
- Файлы Битрикса (`/bitrix/…/x.js`) подключаются минифицированными (`x.min.js`), если копия есть, не пустая и
  не старше исходника, — правило ядра для «Подключать минифицированные версии CSS и JS» (на сайте выключено).
  Ammina отдавала `core.js` минифицированным сама: 229 КБ вместо 511, выполняется на ~25% быстрее (на главной
  на телефоне это одна из длинных задач после первой отрисовки). `js_min` в `?vps_debug=1` — сколько подменено.

## Настройки

Настройки → Настройки модулей → «vspace.pagespeed — скорость загрузки страниц» (первым в списке, сразу под главным
модулем). Одни на весь сайт, включая поддомены;
отключение — списками страниц, доменов и шаблонов сайта. По умолчанию исключены шаблон `demis_group`
(redesign: пока не решено, будет ли он развиваться, поэтому модуль его не обрабатывает и он не замеряется) и
шаблоны старых лендингов: `black_theme`, `black_theme_sidebar`, `black_theme_sidebar_white`, `seo_dark`,
`seo_light` (`/services/seo-prodvizhenie-2/` и соседние), `double_d` (`/double_d/`). Модуль ставится выключенным. Эта инструкция открывается оттуда же —
ссылка «Инструкция по модулю» над вкладками (`/bitrix/admin/vspace_pagespeed_help.php`).

Главное на вкладке «Critical CSS»:

| Настройка | Зачем |
|---|---|
| Блоки контента, блоков в первом экране | где кончается первый экран (по умолчанию шапка + 3 блока) |
| Скрытые при загрузке элементы | мега-меню, попапы: их содержимое не тянет стили в critical |
| Всегда включать классы | cookie-баннер (стоит в футере, виден сразу), виджеты, которые строит JS |
| Не трогать CSS-файлы | оставить файл блокирующим и вне critical |
| Полный CSS блокирует отрисовку на экранах от, px | 1024: на компьютере полный CSS — как без модуля (см. выше), 0 — асинхронно везде |
| Не применять critical CSS на страницах | по умолчанию redesign (`*-redesign/*`, `/redesign/`) — на случай, если шаблон `demis_group` убрать из исключений: веб-шрифт Manrope в TTF приходит позже ранней отрисовки, и его подмена сдвигает первый экран (CLS 0.13 вместо 0.01). Убрать после перевода шрифтов в WOFF2 |

На вкладке «Картинки» — два переключателя (отложенная загрузка и WebP-копии; граница первого экрана и
скрытые элементы берутся с вкладки «Critical CSS»), «Качество WebP» (1–100, по умолчанию 80; готовые копии
с новым качеством пересоздаются кнопкой «Удалить WebP-копии») и состояние WebP: когда агент последний раз запускался из
cron, сколько копий готово, сколько картинок оставлены исходниками и ждут в очереди, кнопка «Удалить
WebP-копии». Если WebP включён, а агент давно не запускался из cron, над вкладками — предупреждение.

На вкладке «JavaScript» — переключатель и «Не откладывать скрипты» (пути файлов или адреса внешних скриптов;
такие скрипты выполняются сразу и не должны зависеть от отложенных — jQuery, BX).

Значения по умолчанию подобраны под шаблоны `demis_edges` и `demis_group` (Config::DEFAULTS).

## Проверка

Администратору (или всем при «Отладочные параметры для всех») доступны параметры:

- `?vps_critical=only` — страница только с critical CSS. Первый экран должен выглядеть как обычно,
  ниже вёрстка может разваливаться — так и задумано. Главный способ проверить настройки;
- `?vps_critical=off` — без critical CSS (полные CSS подключены как обычно), остальное работает: сравнить,
  что даёт сам critical CSS;
- `?vps=off` — без модуля (со всеми блоками Ammina, если она стоит);
- `?vps_debug=1` — статистика: комментарий в конце HTML и заголовок `X-Vspace-PageSpeed`
  (`fold=blocks@81499; critical=hit; critical_bytes=49325; css_files=5; hero=/…/bg-1920.jpg.webp; img_eager=2;
  img_bg=19; webp=77; ms=11.5` — `img_eager`: у скольких картинок снят lazy, `img_lazy`: скольким
  добавлен, `img_bg`: сколько фонов отложено, `webp`: сколько адресов заменено на WebP, `webp_queued` —
  поставлено в очередь этим запросом, `webp_waiting` — уже ждут в очереди, `js_deferred` — сколько скриптов
  отложено, `js_kept` — оставлено на месте). У AJAX-фрагмента — только заголовок.

Ссылки на эти режимы для любой страницы — на вкладке «Кеш и проверка».

Если в первом экране что-то не так: элемент из футера/JS → «Всегда включать классы»; первый экран короче
нужного на конкретной странице → маркер `<!--vps-fold-->` в разметке после последнего видимого блока.

## Установка и выкладка

На рабочий сайт нужны `include.php`, `admin/`, `install/`, `lang/`, `lib/`, `options.php`, `cron.php` (если нет
cron Битрикса) и `README.md` (инструкция в админке), `docs/` — по желанию (анализ Ammina, на него ссылается инструкция). `tests/`, `tools/`,
`vendor/`, `composer.*`, `phpunit.xml` — для разработки.

1. Скопировать модуль в `/local/modules/vspace.pagespeed/`, установить в «Решения Marketplace → Установленные решения».
2. Проверить страницы с `?vps_critical=only` (под администратором), включить модуль.
3. Проверить, что агенты выполняются из cron (раздел «WebP»; нет cron Битрикса — `cron.php`): на вкладке
   «Картинки» агент конвертации должен запускаться раз в минуту. Без cron всё остальное работает, но WebP-копии
   не появятся.
4. Пока Ammina установлена, на обработанных страницах у неё выключаются CSS, lazyload, JS и (когда агент
   WebP работает) картинки (`AMMINA_DISABLE`). От неё остаётся только пересборка страницы через DOMDocument
   (и она по-прежнему срезает у скриптов `data-skip-moving` — поэтому, пока она стоит, такие скрипты тоже
   откладываются, как и у неё). Дальше её можно удалять — см. «План».

## Замеры PageSpeed Insights

`tools/psi.php` — замеры через API Google PageSpeed Insights: оценка и метрики Lighthouse (медиана нескольких
прогонов) и данные реальных пользователей Chrome (CrUX — по ним Google оценивает Core Web Vitals для поиска).
Ключ API — в настройках модуля, вкладка «Кеш и проверка» (скрипт читает его сам, поднимая ядро Битрикса);
можно и `--key=…` или переменной `PSI_API_KEY`.

```
php tools/psi.php --label=ammina                     # до выкладки: 6 типов страниц × mobile/desktop × 3 прогона
php tools/psi.php --label=vspace --compare=ammina    # после: таблица и сравнение «было → стало»
php tools/psi.php --ab --base=https://scilib.ru      # модуль против ?vps=off на одном сайте в одном прогоне
php tools/psi.php --runs=5 /articles/ /services/kontekstnaja-reklama/
```

- PSI заходит на сайт с серверов Google: локальный dmsnew.ru ему недоступен, сайт за паролем (scilib.ru) —
  только с исключением для его запросов. PSI добавляет к User-Agent `Chrome-Lighthouse` (проверено по логу
  nginx scilib.ru, 2026-10-11) — исключение проще всего сделать по нему (так же представляется Lighthouse в
  DevTools, поэтому это не защита, а только исключение для замеров). Если исключение сделано по параметру, его
  можно дописать к адресам: `--query=psi=…`. Страница с ответом 401/404
  считается ошибкой замера, а не оценкой.
- `--ab` работает, только если на сайте включено «Отладочные параметры для всех» (PSI не администратор).
- Повторный запрос того же адреса PSI отдаёт из своего кеша — «три прогона» давали одну оценку трижды
  (до 2026-10-11 медианы в CSV — по сути один прогон). Теперь со второго прогона к адресу дописывается
  `_psi=<число>`; поле (CrUX) берётся из первого прогона, без параметра.
- Результаты дописываются в `tools/psi-results.csv`, справка — `php tools/psi.php --help`. Полевые данные
  усредняются за 28 дней: эффект выкладки в них виден через 2–4 недели.
- Запускать из PowerShell: Git Bash превращает аргумент `/` в путь Windows.

## Ограничения

- Скрипты оживают после загрузки страницы (как и с Ammina): клик по меню до этого момента не сработает.
  Если обработчик `DOMContentLoaded`/`load` вешается не сразу, а позже (в `setTimeout`), загрузчик его не
  увидит. Скрипты, исключённые из откладывания, выполняются раньше отложенных — они не должны зависеть от
  jQuery и BX.
- JS не объединяется и не минифицируется (Ammina делала это на своём сервере): `core.js` Битрикса уходит
  несжатым, 108 КБ по сети вместо ~80 КБ. После удаления Ammina — включить у главного модуля «Подключать
  минифицированные версии CSS и JS файлов» (пока Ammina стоит, эти настройки у Битрикса выключены).
- Внешние CSS (другой домен) не трогаются и остаются блокирующими.
- Обрабатываются `<style>` только из `<head>`; стили в `<body>` остаются на месте.
- Без JavaScript отложенные фоны ниже первого экрана не появятся (как и у Ammina). Поисковики рендерят
  страницы с JS; фоновые картинки в поиск по картинкам не попадают в любом случае.
- Фоны, которые CSS задаёт классами (не в `style`), и картинки, которые вставляет JS, модуль не видит —
  ни для lazyload, ни для WebP (кроме HTML-фрагментов из AJAX). Картинки из CSS-файлов остаются JPEG/PNG
  (на главной — около 100 КБ). В AJAX-фрагментах не подменяются относительные адреса (непонятно, от какой
  страницы их считать). GIF не конвертируется (анимация).
- `width`/`height` у картинок модуль не проставляет. Сдвиг плиток на `/articles/` на телефоне — от скрипта
  `article-list.js`, который подменяет картинку на мобильную с другими пропорциями, — лечится в шаблоне.

## План

1. Удалить Ammina: удалить модуль ammina.optimizer, затем из этого модуля — `Integration/AmminaBridge.php`,
   его вызов в `EventHandler` и настройку `AMMINA_DISABLE`. Включить у главного модуля минифицированные
   версии CSS и JS. Папку `/upload/ammina.optimizer/` не удалять сразу: её WebP-адреса могли попасть в
   поиск по картинкам. Preconnect Ammina (4 домена виджетов) не переносится — эти домены сайт больше не
   использует.
2. По замерам: фон hero главной — 1920 px и на телефоне (в WebP 37 КБ вместо 619 КБ, но мобильная версия
   была бы ещё меньше).

### Отложенные идеи

- **WebP для картинок из CSS-файлов.** Сейчас WebP подменяется только в HTML: `src`, `srcset`, `style`,
  data-атрибуты. `url()` в CSS-файлах и в `<style>` остаются JPEG/PNG — в `main.min.css` таких картинок 37,
  1.6 МБ (браузер качает только используемые на странице; на `/articles/` — `bg_increase-sales.jpg`).
  Вариант: для браузеров с WebP — копия CSS-файла с подменёнными адресами (где копия картинки готова) в
  `/bitrix/cache/css/vspace.pagespeed/`, ссылка на неё вместо исходной, то же в critical. Цена — ещё один кеш,
  который должен обновляться после пересборки CSS. Без модуля — фоны сразу в WebP в SCSS шаблона.
- **Не отрисовывать блоки ниже первого экрана**, пока до них не докрутят: `content-visibility: auto` и
  `contain-intrinsic-size` у блоков верхнего уровня после границы первого экрана. Локально (главная, телефон,
  процессор ×4): включение полного CSS 154 → 108 мс, вставка AJAX-блоков 155/139 → 102/86 мс, выполнение
  скриптов не меняется. Риски: выступающие за блок элементы обрезаются, fixed-элементы внутри блока
  позиционируются от блока, скачет полоса прокрутки. Если вносить — настройкой, выключенной по умолчанию,
  с проверкой страниц на scilib.ru.
